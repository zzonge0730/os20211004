>> A1: Copy here the declaration of each new or changed `struct' or
>> `struct' member, global or static variable, `typedef', or
>> enumeration.  Identify the purpose of each in 25 words or less.
#define DIRECT_BLOCK_COUNT 123
#define INDIRECT_BLOCK_COUNT 128

struct inode_disk {
  off_t length;  // File length in bytes.
  unsigned magic; // File type check.
  block_sector_t direct[DIRECT_BLOCK_COUNT]; // Direct block pointers.
  block_sector_t indirect; // Single indirect block pointer.
  uint8_t unused[8]; // Padding to match BLOCK_SECTOR_SIZE.
};

direct[]: Stores direct block addresses for fast access to small/mid-size files.
indirect: Points to a block containing more block addresses, extending file size.
unused[]: Keeps inode_disk size equal to 512 bytes for block alignment.
>> A2: What is the maximum size of a file supported by your inode
>> structure?  Show your work.
Direct blocks:
123 blocks × 512 bytes/block = 62,976 bytes ≈ 61.5 KB

Indirect block:
128 entries × 512 bytes/block = 65,536 bytes = 64 KB

Total:
62,976 (direct) + 65,536 (indirect) = 128,512 bytes

Maximum file size: 128,512 bytes
---- SYNCHRONIZATION ----

>> A3: Explain how your code avoids a race if two processes attempt to
>> extend a file at the same time.
Our file system uses Pintos’ inode lock to protect concurrent operations:

Before extending a file, a thread holds the inode’s lock.

inode_write_at calls inode_extend while holding this lock.

Therefore, multiple writers cannot corrupt block allocation or length.


>> A4: Suppose processes A and B both have file F open, both
>> positioned at end-of-file.  If A reads and B writes F at the same
>> time, A may read all, part, or none of what B writes.  However, A
>> may not read data other than what B writes, e.g. if B writes
>> nonzero data, A is not allowed to see all zeros.  Explain how your
>> code avoids this race.
When A reads and B writes simultaneously:

Both must acquire the inode’s lock.

inode_read_at and inode_write_at synchronize via this lock.

So, a reader either sees the old data or the new written data, but never uninitialized zero data if the writer wrote non-zero.

This avoids inconsistent reading of a partially written block.


>> A5: Explain how your synchronization design provides "fairness".
>> File access is "fair" if readers cannot indefinitely block writers
>> or vice versa.  That is, many processes reading from a file cannot
>> prevent forever another process from writing the file, and many
>> processes writing to a file cannot prevent another process forever
>> from reading the file.
Pintos’ inode lock is a standard mutex.

Readers and writers acquire the same lock, so no starvation: writers wait for readers to finish, readers wait for writers.

Thus, no indefinite blocking; file access is fair.


---- RATIONALE ----

>> A6: Is your inode structure a multilevel index?  If so, why did you
>> choose this particular combination of direct, indirect, and doubly
>> indirect blocks?  If not, why did you choose an alternative inode
>> structure, and what advantages and disadvantages does your
>> structure have, compared to a multilevel index?
Our inode uses one level of indirect block:

Small to medium files fit in direct blocks for fast lookup.

Larger files use indirect to expand up to ~128 KB.

Not multilevel (no double indirect) to keep code simple and within project scope.

Compared to multilevel, our design is simpler but limits maximum file size.
